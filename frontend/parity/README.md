# Browser parity harness (issue #28; photo sets, issue #116)

Does a browser-hashed original still match the index? This harness answers that with measurements
instead of estimates: it hashes the same synthetic clips twice — once through the server/CLI
pipeline (`matching.fingerprint.PIPELINE`, today `ffmpeg-rgb512-pdq-v1`) and once through the
**real** browser client (`matching.fingerprint.BROWSER_PIPELINE`, today `browser-rgb512-pdq-v1`,
`src/lib/fingerprintClient.ts` in headless Chromium) — and reports the per-frame Hamming distance
between them. Both tags are imported from `matching.fingerprint`, so the report always names the
recipe that actually ran.

The measured numbers live in `docs/adr/0022-frame-sampling-grid.md` (current) and
`docs/adr/0019-browser-fingerprinting-client.md` (the state before the grid fix, issue #70); this
file is how to reproduce them.

**Measured for v1 on 2026-09-18** (issue #29), five runs of the six clips in headless Chromium
153.0.8010.12. The current browser recipe reaches the same table v0 did — pooled **median 2, p90
18, max 30, 0 of 480 rows past either threshold, 30 % identical** — and `--fail-over 36` exits 0.

Getting there took a fix. The first two runs each came back with exactly **8 bad rows** — one
sampled position, all eight orientations — at 60–64 bits in one run and 100–104 in the other, on a
*different* clip each time. The aligned table named the cause without ambiguity: browser offset max
**−1000 ms** with a distance of 2 bits to the frame it actually hashed, i.e. the whole picture was a
second old. `seeked` fires before the seeked-to picture reaches the compositor, and `drawImage`
draws what the compositor has. `fingerprintClient.ts` now waits for `requestVideoFrameCallback`
before drawing (`seekTo`), and three runs since have been clean. The recipe itself did not change,
so the pipeline tag did not either.

**Synthetic media only.** The clips are generated by ffmpeg (`testsrc` / `testsrc2`) at run time and
deleted afterwards unless you pass `--keep-clips`. Never point this at real or pirated media.

## Run it

```bash
make browser-parity                                   # from the repo root
make browser-parity PARITY_ARGS="--keep-clips --duration 20"
```

First run only, from `frontend/parity/`:

```bash
npm install                    # playwright, ~19 MB — deliberately NOT in frontend/package.json
npx playwright install chromium
```

`make check` does **not** run this: it needs ffmpeg, a browser download (see Cost) and about a
minute of decoding per browser. It is an on-demand check — run it when the decode path
(`fingerprintClient.ts`, `videoFingerprint.ts`), the WASM hasher or the server's frame recipe
changes.

## What it does

1. `parity.py` generates the clips with ffmpeg and hashes them with `fingerprint_video` — the
   server's own code, no reimplementation.
2. `browser.mjs` builds `page/` with vite, serves it on loopback, and drives Playwright: the clip
   goes into a real `<input type="file">` and `page/main.ts` calls `fingerprintFile()` — the same
   function the "Add original" panel calls. Nothing is uploaded; the hashes come back through
   `page.evaluate`.
3. `parity.py` compares the two documents per `(frame_index, dihedral)` and writes
   `out/report.md` + `out/report.json` (per-clip median, p90, max, share identical, counts over the
   strict threshold and the loose threshold, both read from `matching/references.py` so
   the report cannot measure against a number the matcher has stopped using, plus a distance
   histogram).

Useful flags: `--browsers chromium,firefox,webkit`, `--duration N`, `--fps F`, `--keep-clips`,
`--regenerate`, `--browser-json FILE` (re-compare an earlier browser run without launching a
browser), `--fail-over 36` (exit non-zero if any distance exceeds N bits).

## Photo collections: `--photos`

```bash
make browser-parity PARITY_ARGS="--photos"
```

The same question for the other shape of original (issue #116, ADR 0053). `parity.py` writes three
sets of the same four synthetic pictures — PNG (lossless), JPEG (quality 92) and WebP (lossless) —
hashes each set with `matching.fingerprint.fingerprint_photos` (`pillow-rgb-pdq-v0`: Pillow → RGB →
PDQ, no scaler, no timeline) and drives the browser through `fingerprintPhotos()`
(`browser-rgb-pdq-v0`: the platform decoder → `OffscreenCanvas` → the same WASM hasher), then
reports the per-image Hamming distance **per format**. Output: `out/report-photos.md` and
`out/report-photos.json`.

What to read in it:

- **`id equal`** — whether both sides computed the same collection digest. A `NO` with a skipped
  count means this browser could not decode one of the pictures, which is a finding about the
  format, not about the hasher.
- **the per-format rows** — PNG should be identical or near it; **JPEG and WebP are the open
  question**, because a browser's decoder is not libjpeg-turbo's and colour management is a hint
  rather than a promise. That gap is the whole reason `browser-rgb-pdq-v0` is a tag of its own
  (ADR 0022's rule), and no number is claimed for it anywhere until this has been run.

No ffmpeg is needed in this mode and there is no alignment table: a collection has no timeline, so
"which moment did each side hash" is not a question that exists. `--keep-clips` keeps the generated
pictures (in `photos/` rather than `clips/`), `--browser-json` re-compares an earlier run, and
`--fail-over N` exits non-zero on a distance past N bits.

## How long it takes: `speed.mjs` (issue #29)

The same page, a different question. `parity.py` asks whether a browser-hashed original still
matches; `speed.mjs` asks whether a creator can sit through the hashing. It drives
`fingerprintFile()` over synthetic clips at 720p, 1080p and 4K H.264 (and HEVC, which headless
Chromium refuses) at 10 and 40 minutes, and reports **seconds of wall time per minute of video**
with the seek, the PDQ hashing and the SHA-256 digest timed apart.

```bash
make browser-speed                                   # the full plan, from the repo root
make browser-speed SPEED_ARGS="--matrix smoke"        # one row, a minute
make browser-speed SPEED_ARGS="--generate"            # write the clips, hash nothing
```

Output: `out/speed*.json` and `out/speed*.md`, rewritten after **every** row, because the full plan
is hours and a crash in the last row must not throw away the first six.

**A slow machine is a cgroup, not DevTools' CPU throttling.** `Emulation.setCPUThrottlingRate`
slows the renderer's main thread and nothing else, and this pipeline spends its time in the media
decoder and in a Worker: at 4× a 720p run moved from 51.6 s to 71.2 s. The device numbers come from
`systemd-run --scope -p AllowedCPUs=… -p CPUQuota=… -p CPUWeight=10000`, which reaches every process
of the browser; the weight is there because this host is shared and a neighbour's `make check` would
otherwise be measured instead of the budget. The three invocations are in the `PLANS` comment in
`speed.mjs`, and the measured table with the whole reasoning is
`docs/research/browser-fingerprinting-speed.md`.

It generates about **15 GB** of clips (a 40 min 4K file is 7 GB) into `speed-clips/`, deleted unless
`--keep-clips` is passed. Each shape is one 60 s x264 encode looped with `-c copy`, so a 40 min file
costs a minute of encoding rather than forty.

## Cost, honestly

- `playwright` npm package: ~19 MB in `frontend/parity/node_modules` (gitignored).
- **Browser binaries: ~658 MB** in `~/.cache/ms-playwright` — outside the repo, shared with every
  checkout on the machine. `playwright install chromium` fetches both the full Chromium (393 MB)
  and the headless shell (261 MB) plus Playwright's ffmpeg (5 MB); the commonly quoted ~150 MB is
  the compressed download, not what lands on disk. Remove it with
  `rm -rf ~/.cache/ms-playwright` when you are done; nothing else in the repo needs it.
- Firefox and WebKit are each a further download and are **not** installed by default.

## In a git worktree

The harness needs the frontend's `node_modules` for vite. Do not `npm ci` a second copy — symlink
the main checkout's:

```bash
ln -s /path/to/marceline/frontend/node_modules frontend/node_modules
ln -s /path/to/marceline/frontend/parity/node_modules frontend/parity/node_modules
```

`.gitignore` says `node_modules/`, which matches a directory and not a symlink to one, so both show
up as untracked: stage explicit paths, and remove the links when you are done.

## Chromium needs NSS on the host

Playwright's Chromium links against the system NSS libraries. On a bare Debian host the launch
fails with `libnspr4.so: cannot open shared object file`. The supported fix needs root:

```bash
sudo apt-get install libnss3 libnspr4      # or: npx playwright install --with-deps chromium
```

Without root, unpack the two packages anywhere and point the loader at them (this is how the
committed numbers were produced):

```bash
cd frontend/parity && mkdir -p .libs/debs && cd .libs/debs
apt-get download libnspr4 libnss3
dpkg-deb -x libnspr4_*.deb ../root && dpkg-deb -x libnss3_*.deb ../root
export LD_LIBRARY_PATH="$PWD/../root/usr/lib/x86_64-linux-gnu"
```

`.libs/` is gitignored; the whole fallback is 6 MB.
